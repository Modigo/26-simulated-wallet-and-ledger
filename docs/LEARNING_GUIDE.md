# Learning guide (beginner-friendly)
**Read in this order:** `backend/app/models/models.py` (tables) → `schemas/schemas.py` (what the API accepts) → `services/users.py` (recipient lookup & phone normalization) → `services/transfers.py` (the money core) → `api/routes.py` (endpoints) → `core/deps.py` + `core/security.py` (sessions/passwords) → `frontend/src/lib/api.ts` → `frontend/src/components/App.tsx`.
**Transfer lifecycle:** form keeps one `idempotency_key` per logical transfer → `POST /transfers` → server derives the sender from the session cookie (never the request body) → locks both wallets in ID order (`FOR UPDATE`, prevents deadlocks/double-spend) → checks balance → updates both balances, writes Transfer + DEBIT(−)/CREDIT(+) entries → one COMMIT. Any exception → ROLLBACK, so a half-transfer is impossible.
**Idempotency example:** you send ₦1,000 with key `abc`; the server commits but your Wi-Fi drops. You retry with key `abc` and the same payload → server finds the existing transfer and returns it — no second debit. Same key, ₦2,000 → 409 conflict.
**Passwords/sessions:** Argon2id hash only; login creates a random token, DB stores SHA-256(token), browser holds it in an HTTP-only cookie; `/auth/me` restores your session after refresh; logout sets `ended_at`.
**Demo vs registered:** demo users have no password and are enterable by design (classroom only); registered users log in with credentials. Both own exactly one wallet; every wallet/transfer query checks ownership.
Try it: break the balance check locally, run `python -m pytest -q`, watch the test fail — then revert.
